Follow-up: the flaky add-lens test was investigated and fixed (same day, OPPO, same device and session).
- Root cause (measured, not guessed): `ActHomeLensManagementWidgetTest.addLens_usesCopiedRowCountForAllApertureBandsAndPreservesSources` read the copied rows after a fixed idle of about 550 ms. The copy runs on Dispatchers.IO after the name dialog confirms (`LensWorkspace.createLens`, then the DAO transaction `duplicateLensLayout`, which is atomic). With a temporary diagnostic that polled for the rows, the first read of the 100-row lens saw 0 rows and all 100 were present 82 ms later; the 10- and 25-row lenses were already complete on the first read. So the product copy is correct and the test raced it.
- Fix: the test now polls up to 5 s for the expected row count (`awaitRows`) before asserting. No production code changed.
- Result, paired runs on the same device right after each other: with the fix 0/30 failures; without it 25/30 failures.
- Earlier unpaired figures (new build 9/12, baseline 11/12 failures) were measured at a different time and are consistent with this.
- OPPO restored exactly again afterwards (18 data files, both APK hashes, packages, settings and /data/local/tmp identical).
