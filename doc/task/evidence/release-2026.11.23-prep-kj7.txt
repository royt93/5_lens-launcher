=== CORRECTION (2026-11-23): "a short tap does not open an app" WAS AN adb ARTIFACT, MY EARLIER READING WAS WRONG ===
What I wrote above in the section "OPEN AN APP FROM THE LENS GRID" ("This is the design, not a fault", "a short tap on an icon launches nothing", "I did not find a user-facing line that tells a new user this") is NOT supported. I tested only with `adb shell input tap`, which sends DOWN and UP about 1 ms apart, and then built a design explanation out of the code. A later measurement on the same release build (apk 8c4f48075314, HEAD 05c92e9a, KJ7, gate first, no ad window, restore DATA-IDENTICAL 207 files):
- `input tap` on the Calculator icon: stayed on ActHome in 7 of 7 rounds.
- Finger held in place with `input swipe x y x y <ms>`: 1 ms and 5 ms stayed (4 of 4 each); 10, 16 and 33 ms opened Calculator (4 of 4 each); 20, 60, 100, 150, 200 and 300 ms opened it (3 of 3 each). Earlier single trials: 400 ms and 900 ms gave the app menu, which follows the system long-press time (300 ms on this phone, `long_press_timeout=300`).
So the threshold sits between 5 and 10 ms. The probable cause, from a comment in LensView (the selected icon index is only refreshed when the grid is drawn, one frame is 16.7 ms at 60 Hz): a touch released before the next frame has no selected icon and launches nothing. This is read from code, not proven with a debugger.
A finger tap on a phone usually lasts tens of milliseconds, so it should open the app, but I did not test with a finger, so I cannot say so for certain.
Consequences: (1) my chat message that new users and Play reviewers tapping the grid "would see nothing happen" had no support; (2) the "first-run hint to lift the finger" I offered was built on that wrong premise and is not needed on this evidence; (3) the release-notes section was rewritten. Not a defect of the app that I can show: a sub-10 ms touch is not something a hand produces.

=== READ ONLY (NO DEVICE RUN): UPGRADE FROM 2026.10.07 WITH SEVERAL LENSES AND LOCKED LENSES (2026-11-23) ===
Question: does going from 2026.10.07 to this build touch the lens-lock state or break a multi-lens setup? What I read, nothing run:
- The lens lock did NOT exist in 2026.10.07: LensLockStore was added after it (commit b418791f). An upgrading user therefore starts with no lock at all: the store reads a missing key as "not locked" (`runCatching { getBoolean(..., false) }.getOrDefault(false)`), so nothing can be locked out by the upgrade itself. The lock state lives in its own file `lens_access_prefs.xml`, which both backup_rules.xml and data_extraction_rules.xml exclude (lines 8 and 8/14), so a cloud restore or device-to-device copy does not carry a lock to a phone where the lock-screen credential may not exist.
- Several lenses already existed at 2026.10.07 (the lens table and its Room v11 migration are older than the release; schema 12 shipped). The upgrade test I ran on the KJ7 and the dense migration test (12 lenses, 3000 rows) cover the data; the lock adds no Room column.
- What the policy does when a lens IS locked (LensAccessPolicy, read, and its unit tests LensAccessPolicyTest pass in the forced gate): the last unlocked lens cannot be locked or deleted (canLock/canDelete), a locked saved-active lens is replaced by the first unlocked one at startup (`resolveActive` returns FALLBACK), and when every lens is locked `resolveActive` returns BLOCKED with no lens id. ActHome.onLensAccessChanged only switches lens when a target id exists.
Not shown: what ActHome does at cold start when the policy says BLOCKED (all lenses locked). The rules above stop the user from reaching that state through the UI (canLock refuses the last unlocked lens), and a locked state cannot arrive by upgrade or restore, so I did not look for a path to it. Unlocking needs a biometric or device credential, which adb cannot drive, so no device run of the lock was made; the earlier 3-lens release smoke did not lock anything.
