=== ROOT CAUSE AND FIX (same day, 19:2x-20:00) ===
Temporary log in HomeSearchController (removed afterwards) on the Pixel, real split top half, T9 off:
  before the fix path: SOURCES decorH=440dp(1543px) windowMetrics=891dp(3120px) displayMetricsH=891dp column=318dp cfgH=891dp appCfgH=441dp
  -> applyKeypadChoice heightDp=891 use=false keypadVis=8 autoShowKb=true (soft keyboard opened).
  So the Activity's own resources Configuration still said 891 dp (it was launched full screen and resized into split) while the decor view was 440 dp. The application context's Configuration said 441. In one earlier run, with the Activity launched after the split existed, cfgH was 441 and the keypad DID show (use=true), which is why the first observation looked inconsistent.
  The policy was right; its input was stale.
Fix (TDD): SearchKeypadPolicy.windowHeightDp(measuredHeightPx, density, configHeightDp) returns the measured window height in dp when the window has been laid out (px > 0, density > 0) and falls back to the Configuration otherwise; HomeSearchController.keypadInUse() now feeds it the decor view height. Tests first (compile-red: 'Unresolved reference windowHeightDp'), then green: SearchKeypadPolicyTest 10/10 (stale 891 vs measured 440 -> keypad; px 0 / negative -> Configuration; density 0 / negative -> Configuration; tall measured window with a short Configuration -> no keypad).
Mutation on windowHeightDp: 8/8 killed (always config, always measured, px >= 0, drop density guard, density >= 0, round up, multiply instead of divide, wrong fallback). The mutation script also hit a 'density >= 0' variant that a stale edit left in the file for a moment; the file was restored and checked (original line present, 1 file changed with 4 insertions in git).
After the fix, same real split via Recents, search opened in the top half: T9 keypad visible (rows 1-6 shown, ABC/DEF/GHI/JKL/MNO), NO soft keyboard (mInputShown=false), list shows one row plus a cut-off row. Screenshot kept in /tmp/f415 (not committed: shows device apps).
